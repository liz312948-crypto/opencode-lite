审查方式：静态源码阅读、现有测试分析、现有质量检查；未连接或测试外部系统，未扫描网络，未执行不受信任命令，未修改核心代码。

## 结论摘要

当前实现已经具备一条清楚、可读、适合教学的串行 safe-editing 主流程：Patch 有大小和格式边界；普通相对路径会被限制在 workspace；审批记录 Patch 内容 SHA-256；命令使用 argv、`shell=False`、workspace cwd 和超时；普通测试失败会触发 reset，并记录 `ExecutionReport`。

但是，这些控制目前还不足以支撑 README 中较强的“不会写源仓库”“严格绑定审批”“bounded output/timeout”“verified rollback”表述。主要缺口是：Windows reparse point 与物理路径身份没有被完整处理；任务工作流没有任务级互斥或 compare-and-swap；审批请求没有携带人工实际审阅的内容摘要；timeout 不管理进程树；rollback 没有绑定不可变的执行前基线；成功报告在测试前生成 diff，无法证明最终保留的 workspace 只包含批准内容；JSON 的多记录更新不是事务。

**总体判断：当前不建议合并到 `main`，也不建议发布 `v0.3.0-alpha`。整体工程风险为“高（存在发布阻断项）”。**

## 2. 相关架构与不变量

safe-editing 的实际调用链为：

```text
API -> SafeEditingService
    -> WorkspaceManager.create_workspace/reset_workspace
    -> PatchApplier.validate/apply/actual_diff
    -> approval fields in JSON Storage
    -> TestRunner.select_command
    -> CommandRunner.run
    -> ExecutionReport + state/log writes
```

审查采用以下工程不变量：

1. Patch 和 harness 自身的文件写入只能落到当前任务的真实 workspace。
2. source repository 在 harness 直接控制的分支中只读；测试代码能否写出 cwd 必须作为单独的信任边界说明。
3. 人工审批必须绑定人工实际看到的 Patch 字节、目标集合和被授权的执行命令。
4. 每个任务同一时刻最多有一个状态推进者和一个 execute attempt。
5. `SUCCEEDED` 必须描述测试结束后的最终 workspace，而不是测试前的中间快照。
6. rollback 必须与不可变的执行前基线比较，不能仅与“当前 source”比较。
7. task、patch、approval、report、status 和 transition log 必须能在崩溃后恢复为一致状态。

## 3. 已确认存在的正向控制

- `PatchProposalCreate.unified_diff` 有 1,000,000 字符模型上限；解析器另有 100 文件、每文件 1,000 hunk 的上限（`models.py:107-113`，`patching.py:13-16,46-104`）。
- Patch 解析器拒绝普通绝对路径、drive 标记、反斜杠、`..`、binary patch、创建/删除、rename、精确字符串重复目标和上下文不匹配（`patching.py:46-104,272-283`）。
- 所有文件内容先在内存准备，再开始落盘；正常写入使用同目录临时文件加 `replace`（`patching.py:106-135,165-179`）。
- 串行流程中，approve 和 execute 都会重算 Patch 内容 SHA-256；未审批 execute 返回 409（`editing_service.py:139-170,194-225`）。
- `CommandRunner` 的直接 `subprocess.run` 调用使用 argv list、`shell=False`、显式 timeout 和 workspace 内 cwd（`runners.py:49-113`）。
- 测试环境按较小白名单重建，常见 API key/secret 不会直接继承；报告会清空 `env_overrides`（`runners.py:14-32,116-130`，`editing_service.py:409-419`）。
- 正常 rollback 失败不会被写成成功：`rollback_succeeded` 初始为 `False`，验证不匹配或异常会保留失败并追加错误信息（`editing_service.py:339-391`）。
- README 和 `docs/safe-editing.md` 已明确说明测试代码不是 OS sandbox，并明确 JSON 多 worker 不受支持。

## 5. 详细发现

### FS-01 — Windows reparse point 与物理路径身份未纳入 workspace 边界

- **等级：发布阻断**
- **对应文件和代码位置：** `repopilot_lite/workspace.py:29-32,43-81,92-123`；`repopilot_lite/tools.py:77-123,203-221`。
- **触发条件：** source、workspace root 或任务目录包含 Windows junction/其他 reparse point，或者同一物理目录通过不同 Windows namespace/规范化形式表示。
- **对正确性或数据完整性的影响：** copy ignore 只检查 `Path.is_symlink()`，没有处理 junction；路径包含关系只比较 `Path` 值和 `parents`，没有验证同一文件系统对象。结果是 copy、snapshot 或 repository search 可能跨过提交目录的物理边界；workspace cleanup 也只确认“位于 base 下”，没有确认它仍是该 task 的原始目录。对 Windows 优先支持的项目，这不足以证明 source 与 workspace 永不互相包含，也不足以证明一个任务不会影响另一个任务的 workspace。
- **当前测试覆盖情况：** `tests/test_workspace.py:10-50` 只覆盖普通目录、常见 ignore 目录、普通 reset 和一个 `../` task ID；没有 symlink、junction、UNC、extended namespace、路径大小写、same-file 或跨任务 workspace identity 测试。
- **最小防御性修复建议：** 对 source、base、task root 及每个遍历组件拒绝所有 reparse point；Windows 上使用最终句柄路径和 volume/file ID 判断真实身份与包含关系；workspace 只能是新建的、不可预先存在的 `base/<validated-task-id>`，并在 cleanup/reset 前再次验证 task 到目录身份的绑定；明确拒绝 base root 本身作为 cleanup 目标。
- **建议增加的测试：** file symlink、directory symlink、junction、nested reparse、UNC、extended namespace、大小写别名、预先存在的 task 目录、跨任务目录映射；断言 copy/search/snapshot 不读取边界外内容，reset/cleanup 只能作用于登记给当前 task 的目录。

### FS-02 — Patch 检查与最终写入之间存在目录拓扑变化窗口

- **等级：发布阻断**
- **对应文件和代码位置：** `repopilot_lite/patching.py:106-135,165-179,286-295`；`repopilot_lite/editing_service.py:223-244`。
- **触发条件：** dry-run、`_prepare_changes`、临时文件创建和 `replace` 之间，目标文件或祖先目录的 reparse/rename 状态发生变化。
- **对正确性或数据完整性的影响：** `_resolve_inside` 返回解析后的字符串路径，随后 `target.is_symlink()` 检查的是解析结果，而不是最初路径组件；真正写入时没有持有已验证目录的不可替换句柄。即使早先的 containment 成立，最终 `mkstemp`/`replace` 仍可能面对不同的文件系统拓扑，因此“Patch 不能写 workspace 外”不是稳定不变量。
- **当前测试覆盖情况：** `tests/test_patching.py:18-70` 覆盖普通 dry-run、普通 traversal 和上下文失败；没有 reparse ancestor、检查/使用状态变化或最终句柄路径验证。
- **最小防御性修复建议：** 在 workspace 独占锁内完成 validate+apply；逐级 no-follow 打开目录/文件并基于句柄写入，Windows 上校验最终句柄路径仍位于已登记 workspace；在每次 replace 前重验文件 identity、parent identity 和 reparse 属性。无法提供原子 no-follow 保证的平台应拒绝相关文件系统类型。
- **建议增加的测试：** 用受控文件系统测试替身在 validate/apply 边界改变目录 identity，断言写入被拒绝且 workspace 外哨兵不变；覆盖直接 symlink、祖先 junction、目标 rename 和最终 replace 前重验。

### WF-01 — 无任务级互斥/CAS，并发请求可重复执行和覆盖状态

- **等级：发布阻断**
- **对应文件和代码位置：** `repopilot_lite/main.py:78-113,132-202`；`repopilot_lite/storage.py:27-76`；`repopilot_lite/editing_service.py:66-191,194-324`；`repopilot_lite/state_machine.py:12-40`。
- **触发条件：** 同一 task 同时收到 approve/reject、两个 execute、两个 submit，或 run 与 editing 请求；每个请求先读取自己的 `TaskRecord` 快照。
- **对正确性或数据完整性的影响：** 状态机只验证内存对象的旧状态，`Storage.update_task` 不比较持久化 revision。两个 stale 快照都能各自通过合法边校验，然后后写覆盖先写；可能重复 apply/运行命令、让 reject 与 execute 交错、产生重复 transition log，甚至让磁盘上的实际状态序列出现状态机未允许的边。`execute` 的成功幂等分支只处理已经完成后的串行重试，不能防止进行中的重复执行。
- **当前测试覆盖情况：** `tests/test_state_machine.py:16-44` 只测试单对象合法/非法跳转；`tests/test_execution_api.py:54-56` 只测试成功结束后的重复 execute；没有并发请求或 stale object 测试。
- **最小防御性修复建议：** 为每个 task 建立互斥/lease；为任务记录增加单调 revision，并在状态更新中做 compare-and-swap；execute 创建唯一 attempt ID 和幂等键，只有一个 attempt 能从 AWAITING_APPROVAL 取得执行权；approve/reject/submit 同样在同一事务内检查 current patch 和 revision。
- **建议增加的测试：** 并发双 execute、approve/reject 竞态、reject/execute 竞态、双 submit、run/execute；断言命令只运行一次、最终状态唯一、日志边全部合法、旧 revision 返回 409。

### AP-01 — 审批未绑定客户端实际审阅的 hash，且未绑定执行命令

- **等级：发布阻断**
- **对应文件和代码位置：** `repopilot_lite/models.py:44-48,115-117,120-132`；`repopilot_lite/editing_service.py:139-170,194-237`；`repopilot_lite/storage.py:118-125`。
- **触发条件：** 人工 GET diff 后、POST approve 前，Patch 记录被并发工作流、恢复逻辑或直接 JSON 修改改变；或者批准后 task 的 `test_command`/timeout 被改变。重复 approve 还会在 `APPROVED + approved_patch_id` 时提前返回，早于内容重验。
- **对正确性或数据完整性的影响：** `PatchDecision` 只有 `patch_id`。服务记录的是“approve 时服务端当前内容”的 hash，而不是客户端明确回传的“人工刚看到内容”的 hash；命令也不属于批准元组。因此当前设计能防止普通串行流程中旧 ID 批准新 ID，却不能严格证明人工动作绑定了其实际审阅的字节和最终执行命令。
- **当前测试覆盖情况：** `tests/test_patch_api.py:38-79` 覆盖错误 ID 和 `approved_hash == proposal.content_hash`；没有 GET/approve 间内容变化、hash 替换、stale approval、批准后命令变化、重复 approve 重验或并发 reject。
- **最小防御性修复建议：** approve 请求必须携带 expected SHA-256（或使用 `If-Match`/ETag）；Patch 采用 append-only/content-addressed 记录；批准对象至少包含 `task_id + patch_id + content_hash + canonical target set + canonical command hash + task revision + expiry`；execute 在持有任务锁的同一事务中重新加载并比较完整批准元组。
- **建议增加的测试：** GET 后内容摘要变化必须返回 409；Patch ID 相同但内容、目标元数据或命令变化必须重新审批；reject 后 execute 永远失败；重复 approve 仍重验 hash；旧 approval 不能跨 attempt/revision 使用。

### CR-01 — timeout 不管理进程树，不能形成可靠 rollback 屏障

- **等级：发布阻断**
- **对应文件和代码位置：** `repopilot_lite/runners.py:60-90`；`repopilot_lite/editing_service.py:256-291,327-391`；README `369,381`。
- **触发条件：** pytest/npm 或其插件派生子进程/孙进程，或者后代仍持有输出管道。
- **对正确性或数据完整性的影响：** `subprocess.run(..., timeout=...)` 只能直接管理创建的进程，没有 POSIX process group 或 Windows Job Object。直接进程超时不等于进程树全部退出；rollback 可能在仍有后代持有资源或稍后继续写文件时执行和验证。README 已承认不能保证所有 descendant 清理，但这与“timeout 后 verified rollback”的核心结果字段仍存在语义冲突。
- **当前测试覆盖情况：** `tests/test_runners.py:46-59` 只有单进程 sleep；`tests/test_execution_api.py:94-129` 只有普通慢 pytest；没有 process tree、管道继承、残留 PID 或 rollback 后延迟写入测试。
- **最小防御性修复建议：** 改用 `Popen`；POSIX 创建新 session 并终止 process group，Windows 使用带 `KILL_ON_JOB_CLOSE` 的 Job Object；等待进程树退出并经过短暂稳定窗口后才 reset/verify；无法确认清理时将 report 标为 rollback 未验证，而不是成功。
- **建议增加的测试：** 子进程、孙进程、继承/关闭输出管道、忽略温和终止、超时后写入；断言 timeout+grace 是墙钟上界、无残留 PID、rollback 验证后 workspace 不再变化。

### RB-01 — rollback 使用当前 source，而非不可变执行前基线

- **等级：发布阻断**
- **对应文件和代码位置：** `repopilot_lite/workspace.py:92-112`；`repopilot_lite/editing_service.py:66-128,327-391`。
- **触发条件：** proposal/approval/execution 之间 source 内容发生变化，或 snapshot 过程中 source/workspace 继续变化。
- **对正确性或数据完整性的影响：** reset 会重新复制 `task.source_repo_path` 的当前内容，随后比较两个当前 snapshot；没有持久化 proposal 时或 execute 前的 source manifest。于是 `rollback_succeeded=True` 只能表示“刚恢复的 workspace 与比较时的当前 source 内容哈希一致”，不能表示“恢复到执行前基线”。snapshot 还只比较普通文件字节，不比较 mode、空目录、reparse identity，并跳过 ignore/symlink。
- **当前测试覆盖情况：** `tests/test_workspace.py:30-43` 和 `tests/test_execution_api.py:69-129` 都保持 source 静态，主要比较单文件字节；没有 source drift、文件集合变化、权限/空目录、snapshot race 或 immutable baseline 测试。
- **最小防御性修复建议：** workspace 创建后保存不可变 baseline manifest（相对路径、大小、hash、必要元数据、source identity/revision）；execute 前再次确认 source 未漂移；rollback 从受保护的 baseline 副本恢复，而不是重新读取活动 source；比较应在 workspace 独占锁内完成。
- **建议增加的测试：** proposal 后 source 改动、增加/删除文件、权限或空目录变化、snapshot 期间变化；断言 source drift 阻止 execute，rollback 精确恢复保存的 baseline。

### RB-02 — `SUCCEEDED` 不能证明测试后的最终 workspace 等于批准结果

- **等级：发布阻断**
- **对应文件和代码位置：** `repopilot_lite/editing_service.py:239-267,307-324,395-428`；`repopilot_lite/patching.py:139-162`。
- **触发条件：** 测试、插件或构建步骤在运行期间修改目标文件或其他非忽略文件，但测试退出码为 0。

- **当前测试覆盖情况：** 没有多实例/多进程测试，也没有启动配置防护测试。
- **最小防御性修复建议：** v0.3 启动时取得 data-dir 独占锁并明确拒绝第二实例；文档和启动示例固定 `--workers 1`。完整事务和多 worker 支持可移至 v0.4 SQLite。
- **建议增加的测试：** 第二实例/worker 启动失败且信息明确；文档示例和配置测试固定单 worker。

### LIM-03 — 当前审批是本地单操作者动作，不是独立身份审批

- **等级：已接受限制**
- **对应文件和代码位置：** `repopilot_lite/main.py:25-36,55-202`；README `71-74,297-309`。
- **触发条件：** 服务被绑定到不受信任网络或存在多个需要隔离的使用者。
- **对正确性或数据完整性的影响：** API 没有认证、授权或审批者身份；“人工审批”在当前模型中表示一次显式 API 动作，而不是任务创建者与独立审批者之间的权限隔离。对本人维护的 loopback 教学项目可以接受，但不应被描述为多用户审批控制。
- **当前测试覆盖情况：** 所有 API 测试都由同一个 `TestClient` 创建、审批和执行；没有身份/权限测试。
- **最小防御性修复建议：** v0.3 强制或明确默认 loopback，启动时警告非 loopback；可增加本地随机 token。多人身份、角色和租户隔离可放入后续版本。
- **建议增加的测试：** 启动配置拒绝无显式确认的非 loopback；若加入 token，覆盖缺失/错误 token 和 task ownership。

## 7. 文档准确性

当前文档准确的部分：

- `subprocess.run` 的直接调用确实是 argv list 和 `shell=False`。
- cwd 在稳定目录拓扑下会 resolve 并限制到 workspace。
- test environment 不直接继承 `OPENAI_API_KEY` 等常见 secret。
- 项目明确不是 OS sandbox，只应运行可信仓库。
- JSON 多 worker 不受支持已经明确写入 README 和 architecture。
- `SUCCESS` 与 `SUCCEEDED` 的区别已有解释。

需要收窄或修正的表述：

- “never writes to submitted source”应限定为 harness-managed 文件操作，并说明测试代码例外。
- “all symlinks are skipped”不能覆盖 Windows junction/所有 reparse point。
- “immutable proposal”和“approval binds exact patch”需要 expected hash/不可变记录/事务支持后才严格成立。
- “bounded output”目前只是持久化前截断，不是运行时内存边界。
- “timeout + verified rollback”需要进程树退出、不可变 baseline 和 post-rollback 稳定性验证。
- “atomic JSON writes”只适用于单个文件的正常 replace，不能表达跨 task/log/patch/report 事务或 crash durability。

## 8. 发布决策

### 1. 当前是否适合合并到 main

**不适合。** v0.3 的主要卖点是 Safe Editing Harness，而 FS-01/FS-02、WF-01、AP-01、CR-01、RB-01/RB-02、ST-01、PA-01 和 CR-02 都直接影响其核心不变量。即使定位为 alpha，也不宜把这些行为随强安全表述合入 main。

### 2. 当前是否适合发布 v0.3.0-alpha

**不适合。** 现有 30 个测试、Ruff 和 Mypy 全过，说明基础实现质量良好，但发布门禁缺少 Windows reparse、并发、process tree、immutable rollback baseline、final workspace integrity 和 storage fault recovery。

### 3. 发布前必须修复什么

1. 对 Windows symlink/junction/reparse、namespace alias 和 task workspace identity 建立物理边界校验；消除 patch write TOCTOU。
2. 增加任务级 lock/lease、revision CAS、唯一 execution attempt 和真正的并发幂等。
3. approve 绑定客户端 expected Patch hash、canonical targets、command hash 和 task revision；Patch 记录不可变。
4. timeout 管理完整进程树，确认退出后再 rollback。
5. 保存不可变 execution baseline；rollback 与该 baseline 比较；测试后验证最终 workspace 与批准结果一致。
6. 让 task/patch/approval/report/status/log 能事务提交或可崩溃恢复；准确记录部分 apply。
7. 固定可信 executable identity，而不是仅检查 basename。
8. 为以上各项添加 Windows、并发、故障注入和内容一致性发布门禁测试。

CR-03、ST-02、API-01、LOG-01 至少也应在发布前完成最小缓解和准确文档：真正的流式输出预算、单实例锁/恢复策略、请求与 copy 配额、统一脱敏。

### 4. 哪些问题可以放入 v0.4

- SQLite 的完整多 worker/多进程支持；v0.3 先强制单实例。
- 独立身份、角色、多人审批和 tenancy；v0.3 保持 loopback 单操作者边界。
- 容器/VM/低权限账户等 OS sandbox；v0.3 必须清楚保持“可信仓库”限制。
- 状态拆分、attempt 历史 API、`SUCCESS`/`SUCCEEDED` 命名清理。
- 更丰富的文件元数据、长期审计留存和策略化产物白名单。

### 5. 当前整体工程风险

**高。** 风险不是普通代码风格问题，而是核心隔离、审批、并发、rollback 和持久化证据在非 happy path 下不能形成闭环。修复发布阻断项后，项目可以成为结构清楚、边界诚实的教学 alpha；在此之前，应避免把当前实现描述为已经验证的 Safe Editing Harness。

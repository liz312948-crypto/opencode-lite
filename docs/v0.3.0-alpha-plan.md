# OpenCode-Lite v0.3.0-alpha Implementation Plan

## Audit Summary

The current repository is a small FastAPI application whose Python sources live in
`repopilot_lite/`; there is no `src/` directory. The public API is defined in
`repopilot_lite/main.py`, and all existing endpoints are synchronous.

Current call flow:

```text
POST /tasks
  -> JSON Storage
POST /tasks/{task_id}/run
  -> Planner
  -> Executor
  -> ToolRegistry
  -> list/read/search/summarize tools
  -> JSON Storage + StepLog
```

Existing responsibilities:

- `models.py`: Pydantic task, plan, result, log, and status models.
- `main.py`: FastAPI application, dependencies, and routes.
- `planner.py`: fixed repository-analysis plan.
- `executor.py`: sequential plan execution and bounded keyword-search retry.
- `tools.py`: registry, repository readers, search, and rule/LLM summarization.
- `llm_client.py`: optional OpenAI-compatible summarizer with rule fallback.
- `storage.py`: lock-protected JSON persistence for tasks and logs.
- `tests/test_api.py`: three API tests covering analysis, retry, and tool listing.

The current status flow is `PENDING -> PLANNING -> RUNNING -> SUCCESS|FAILED`.
`Storage.update_status` currently permits arbitrary assignment and state changes are
not logged as dedicated transition events. The repository path is resolved by tools,
but no isolated writable copy exists. JSON persistence is sufficient for the alpha
provided that patch records and expanded task/report models are added; a database
migration is not required.

Baseline verification on Python 3.12.10: `3 passed`. Ruff and mypy were not installed
in the current environment, so they will be added to the development dependencies.

## Compatibility And Naming Strategy

The external project name, metadata, API title, and documentation will become
OpenCode-Lite. The internal Python package remains `repopilot_lite` for v0.3 to avoid
breaking imports, persisted module references, and the existing Uvicorn command.
Existing endpoints and the legacy `SUCCESS` analysis status remain supported.

The README will state that OpenCode-Lite is an independent educational and engineering
project and is not affiliated with or endorsed by the OpenCode project.

## Target Architecture

```text
Task API -> Planner -> Executor -> ToolRegistry -> repository understanding
                              |
                              v
WorkspaceManager -> PatchProposal -> Approval Gate -> PatchApplier
                                                       |
                                                       v
                                              TestRunner/CommandRunner
                                                       |
                                                       v
                                          ExecutionReport -> success/rollback
```

The safe-editing path is additive. It consumes the existing analyzed task and stores
all mutations in a per-task temporary workspace. It never writes to `repo_path`.

## New Data Models

- `PatchProposalCreate`, `PatchProposal`, `PatchDecision`, and `PatchValidationStatus`.
- `CommandSpec` and `CommandResult`.
- `ExecutionReport` attached to `TaskRecord`.
- Task fields for source/workspace paths, current/approved patch IDs, test command,
  timeout, `error_code`, and `error_message` while retaining the legacy `error` field.
- Structured API errors represented in `HTTPException.detail` with `error_code` and
  `message`.

## Task States And Transitions

New states: `PATCH_PROPOSED`, `AWAITING_APPROVAL`, `APPLYING_PATCH`, `TESTING`,
`ROLLING_BACK`, `SUCCEEDED`, and `CANCELLED`. Existing `SUCCESS` remains the terminal
state of the compatible repository-analysis flow.

Primary transitions:

```text
PENDING -> PLANNING -> RUNNING -> SUCCESS
                    |          -> FAILED
                    -> FAILED

SUCCESS|FAILED|CANCELLED -> PATCH_PROPOSED
PATCH_PROPOSED -> AWAITING_APPROVAL|FAILED|CANCELLED
AWAITING_APPROVAL -> APPLYING_PATCH|CANCELLED
APPLYING_PATCH -> TESTING|ROLLING_BACK
TESTING -> SUCCEEDED|ROLLING_BACK
ROLLING_BACK -> FAILED
FAILED|CANCELLED -> PLANNING (compatible rerun)
```

Every transition is validated centrally and written as a `StepLog`. Illegal jumps
raise a domain error. Patch generation retries, patch application retries, and test
retries are all fixed at zero in this alpha; the existing search retry remains capped
at two attempts.

## API Changes

Existing endpoints stay unchanged:

- `POST /tasks`
- `POST /tasks/{task_id}/run`
- `GET /tasks/{task_id}`
- `GET /tasks/{task_id}/logs`
- `GET /tools`

New endpoints:

- `POST /tasks/{task_id}/patches`: submit and dry-run validate a unified diff.
- `GET /tasks/{task_id}/diff`: inspect the current immutable patch proposal.
- `POST /tasks/{task_id}/approve`: approve one exact `patch_id` and content hash.
- `POST /tasks/{task_id}/reject`: reject one exact `patch_id`.
- `POST /tasks/{task_id}/execute`: apply the approved patch in the workspace and run
  a bounded, explicitly selected test command.

`TaskCreate` gains optional `test_command` and `test_timeout_seconds`; old request
bodies remain valid.

## Security Boundary

- Harness-managed patch, reset, cleanup, and command-cwd operations never target the
  source repository; trusted test code is not an OS write sandbox.
- A task-specific temporary workspace is created with ignored cache/build directories.
- Symlinks, junctions, and other reparse points are rejected during traversal rather
  than silently followed or skipped.
- Patch paths must be relative POSIX-style paths without drive letters, absolute paths,
  backslashes, `..`, symlink escapes, binary patches, renames, creates, or deletes.
- Every patch is parsed and applied in memory as a dry run before any file write.
- Approval requires the client-reviewed SHA-256 and binds patch ID, content hash,
  normalized command hash, and task revision; modified/stale tuples require approval.
- Commands use an argv list, `shell=False`, a workspace-contained `cwd`, a mandatory
  timeout, limited output, and a minimal inherited environment.
- Only explicit `pytest`, `python -m pytest`, or `npm test` command shapes are accepted.
- LLM output cannot select or execute shell commands and cannot bypass approval.
- On application/test failure the workspace is deleted and recopied from the source;
  baseline/source manifests and bounded failure evidence stay in JSON records.

This is workspace and process-lifecycle containment, not an operating-system sandbox.
Repository tests still execute with the permissions of the API process.

## Known Risks

- JSON files use revision checks, atomic replacements, and a redo journal adequate for
  a single-process prototype, but do not provide cross-process locking, a durable
  command supervisor, or production tenancy.
- `subprocess.Popen` cleanup uses POSIX process groups and a fail-closed Windows Job
  Object. This is not a container or OS permission sandbox.
- The pure-Python patch engine intentionally supports text-file modifications only; it
  rejects binary patches, renames, file creation/deletion, and advanced Git diff forms.
- Workspace copies can be expensive for large repositories even with ignore rules.
- Retaining the internal `repopilot_lite` package creates temporary brand/package naming
  asymmetry, documented as a compatibility choice for v0.3.
- Persisted v0.2 tasks remain readable because old fields and `SUCCESS` are retained;
  editing those tasks still requires a valid source path and a newly created workspace.

## Explicitly Out Of Scope

- GUI, TUI, IDE integration, or a full OpenCode replacement.
- Editing, merging, pushing, or opening pull requests against the source repository.
- Multi-agent workflows, MCP, RAG, vector databases, LSP, AST indexing, or long-term memory.
- Docker/VM sandboxing, arbitrary shell access, cloud deployment, or production tenancy.
- SQLite/PostgreSQL migration and a large dynamic-planner or LLM planner redesign.

Potential v0.4 work includes storage migration, dynamic planning, AST-aware indexing,
stronger process isolation, and evaluator-style patch review.

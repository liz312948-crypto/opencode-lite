# OpenCode-Lite v0.3.0-alpha 发布阻断修复计划

日期：2026-07-11  
基线：`fix/opencode-lite-v0.3-release-blockers` / `da5acb5`  
依据：`docs/v0.3-reliability-review.md`

## 目标与边界

本轮只修复可靠性审查中的“发布阻断”以及闭环所需的少量“应尽快修复”项。不增加 UI、TUI、MCP、多 Agent、AST/向量索引、动态 Planner、源仓库写回、PR 自动化或其他业务功能。

实现保持 v0.2 分析 API 兼容。v0.3 尚未发布的 approve 请求将增加人工实际审阅的 Patch SHA-256；这是唯一计划内的请求体收紧。所有文件系统与进程测试只使用 pytest 临时目录和本项目自身的子进程，不访问外部系统。

## 架构决定

1. **保守文件系统策略。** v0.3 拒绝 source/workspace 树中的 symlink、Windows junction 和其他 reparse point，不尝试安全跟随。所有 Patch 目标统一经过同一套最终路径与组件 identity 检查。
2. **单进程任务串行化。** 增加有界、引用计数的每任务 `RLock` 管理器；锁在无持有者/等待者时移除。它只承诺单进程并发安全，文档固定单 Uvicorn worker。
3. **审批元组。** approve 绑定 `task_id + patch_id + content_hash + normalized command hash + task revision`。Patch 内容在创建后不可变，execute 在锁内重新加载并重验。
4. **manifest 基线。** apply 前保存 workspace/source manifest；测试后验证最终 workspace；失败时 reset 后与 apply 前 manifest 比较。manifest 至少包含相对路径、类型、大小与 SHA-256。
5. **进程树与流式输出。** 使用 `Popen`、POSIX process group、Windows Job Object/受控平台回退，超时终止整棵树；stdout/stderr 增量读取并限制内存。
6. **继续使用 JSON。** v0.3 不迁移 SQLite。单文件写使用唯一同目录临时文件、flush/fsync、`os.replace`；跨文件 bundle 使用 write-ahead transaction journal，启动时前向恢复。Storage 接口保持兼容。
7. **诚实的残余边界。** Python 路径检查无法抵御拥有同一 OS 账户权限、在最终系统调用瞬间并发改写目录拓扑的外部进程；本轮通过拒绝 reparse、任务锁、写前重验和可信仓库/单操作者边界把风险降到 v0.3 教学 alpha 可接受范围。真正面向不可信本机对手仍需要低权限进程与 OS sandbox。

## 逐项修复映射

### FS-01 — Windows reparse point 与物理路径身份

- **涉及文件：** `repopilot_lite/workspace.py`、`repopilot_lite/tools.py`、`tests/test_workspace.py`。
- **根因：** copy/snapshot 只判断 `is_symlink()`；包含关系依赖 lexical `Path.parents`；workspace cleanup 未确认直接 task root 与 reparse-free identity。
- **最小修复：** 新增跨平台 link/reparse 检测；安全遍历 source/workspace；拒绝任何链接组件；使用 existing-path same-file/ancestor identity 补强 Windows namespace 别名；cleanup/reset 仅允许 base 的直接、无链接 task child。
- **状态/API 兼容性：** 路径违规继续映射为结构化 workspace/patch 422；正常路径和响应模型不变。此前被静默跳过的 symlink 仓库将被明确拒绝。
- **新增测试：** symlink 文件、symlink 目录、Windows junction（平台支持时）、namespace/大小写 identity、预先存在 reparse task root、source manifest 不变。
- **验收标准：** copy/snapshot/reset/cleanup 不跟随链接；source 与 workspace 的真实身份不能互相包含；只有登记的 task child 可删除。

### FS-02 — Patch 检查/使用状态变化窗口

- **涉及文件：** `repopilot_lite/patching.py`、`repopilot_lite/workspace.py`、`repopilot_lite/editing_service.py`、`tests/test_patching.py`。
- **根因：** `_resolve_inside` 后仅保存字符串 `Path`；`is_symlink()` 在 resolve 后执行；temp/write/replace 前没有统一重验目标 identity。
- **最小修复：** PatchApplier 使用 workspace 的统一安全解析器；prepare、临时文件创建、replace 前后都重验祖先组件、最终路径、文件 identity 与 workspace containment；整个 validate/apply/execute 在 task lock 内。
- **状态/API 兼容性：** 新的路径异常仍为 `PATCH_VALIDATION_FAILED`；正常 unified diff 行为不变。
- **新增测试：** 最终目标解析出 workspace、链接目标/祖先、写前受控 identity 变化、source hash 不变。
- **验收标准：** 任一阶段发现 target/parent identity 变化即在写入前失败并进入明确 rollback；PatchApplier 从不接收 source 作为写根。

### WF-01 — 并发 execute 与 stale task 状态

- **涉及文件：** `repopilot_lite/task_locks.py`（新增）、`main.py`、`editing_service.py`、`storage.py`、`tests/test_execution_api.py`、`tests/test_state_machine.py`。
- **根因：** 每个请求在锁外读取独立 `TaskRecord`；状态机只校验本地旧状态；Storage 更新无 revision/CAS。
- **最小修复：** 有界每任务锁覆盖重新加载、前置条件、状态推进、apply/test/rollback 与报告提交；TaskRecord 增加单调 revision，Storage bundle 写验证 expected revision；并发重复 execute 等待首个 attempt，随后确定性返回已成功结果或 409 失败状态。
- **状态/API 兼容性：** 成功后的重复 execute 保持 200+同一报告；进行中并发请求不再启动第二命令；失败后的重复 execute 保持明确 409。新增 revision 为响应兼容字段。
- **新增测试：** 双 execute 只执行一次、reject/execute 顺序、stale revision、非法状态边、状态与 ExecutionReport 一致。
- **验收标准：** 单进程内同 task 任何时刻只有一个 mutating workflow；持久化 log 中没有由 stale snapshot 形成的非法边。

### AP-01 — 人工审批内容与命令绑定

- **涉及文件：** `models.py`、`editing_service.py`、`runners.py`、`storage.py`、`main.py`、API/README 文档、`tests/test_patch_api.py`。
- **根因：** approve body 只有 patch_id；重复 approve 在 hash 重验前返回；test_command 不属于批准摘要；Patch 更新接口未强制内容不可变。
- **最小修复：** 为 approve 使用 `PatchApproval(patch_id, content_hash)`；验证人工 expected hash；持久化 approved patch hash、规范化 command hash 与 task revision；Storage 拒绝修改已创建 Patch 的 diff/hash；execute 锁内重新加载、重算并比较完整批准元组。
- **状态/API 兼容性：** v0.2 API 不受影响；v0.3 approve body 新增必填 `content_hash`，diff 响应已有该值；reject 仍只需 patch_id。
- **新增测试：** stale approval、内容变化、命令变化、重复 approve 重验、reject 后 execute、旧 revision approval。
- **验收标准：** execute 的 Patch 字节、目标集合和命令与人工批准元组完全一致；任一不一致返回 409 且不 apply/不运行命令。

### CR-01 / CR-02 / CR-03 — 进程树、可信 executable 与输出预算

- **涉及文件：** `runners.py`、`models.py`、`editing_service.py`、`tests/test_runners.py`、`tests/test_execution_api.py`。
- **根因：** `subprocess.run` 只控制直接进程；argv[0] 只检查 basename；输出先完整 capture 再截断。
- **最小修复：** 规范化 pytest/python 到可信 `sys.executable -m pytest`，npm 固定启动时解析的真实路径；拒绝 argv[0] 路径逃逸；`Popen` 分平台建立 process group/job；线程增量 drain 两个 pipe，达到字节预算后丢弃剩余；timeout 有限 grace 后终止/强杀整组并记录 cleanup 结果。
- **状态/API 兼容性：** 允许的逻辑命令形状不变；报告增加 process cleanup 字段；显式外部同名 executable 改为拒绝。
- **新增测试：** executable identity、父子进程 timeout、无残留哨兵、输出预算、UTF-8、cleanup failure（平台限制时明确 skip）。
- **验收标准：** `shell=False`/argv 保持；timeout+grace 有墙钟上界；父子进程均终止；内存保存输出不超过预算；环境值不进入报告。

### RB-01 / RB-02 — rollback 基线与最终 workspace

- **涉及文件：** `workspace.py`、`editing_service.py`、`models.py`、`tests/test_workspace.py`、`tests/test_execution_api.py`。
- **根因：** reset 与当前 source 比较；没有持久化 execute 前 manifest；diff 在测试前计算，成功后不验证 workspace 漂移。
- **最小修复：** 安全 manifest 包含目录/普通文件的相对路径、类型、大小、SHA-256；apply 前确认 workspace==source 并保存 baseline；apply 后保存 expected manifest；测试后必须等于 expected manifest；失败 reset 后必须等于 baseline；同时比较 source before/after 并在报告中记录 manifest hashes、source_unchanged 和 rollback_error。
- **状态/API 兼容性：** 现有 ExecutionReport 字段保留并增加可选完整性字段；测试修改非忽略文件即转为失败+rollback；rollback 失败最终仍为 FAILED，但有独立错误信息。
- **新增测试：** 修改/新增/删除后的 rollback、timeout rollback、source drift、post-test mutation、rollback failure、文件集合和内容恢复。
- **验收标准：** 只有 reset manifest 精确等于 execute 前 baseline 才可 `rollback_succeeded=true`；只有测试后 manifest 等于 approved post-patch manifest 才可 `SUCCEEDED`。

### ST-01 / ST-02 — JSON 原子性与跨记录一致性

- **涉及文件：** `storage.py`、`editing_service.py`、`executor.py`、`main.py`、`tests/test_storage.py`（新增）。
- **根因：** 固定 `.tmp` 名、无 flush/fsync；task/log/patch/report 分多次 replace；崩溃可留下半提交；实例锁不跨进程。
- **最小修复：** 唯一同目录 temp、flush+fsync、`os.replace`、目录 fsync（平台支持时）；bundle 写先持久化 transaction journal，再幂等写目标，最后删除 journal；初始化时前向恢复；transition 与关联 log 同 bundle；approval/report/patch 状态按一个 bundle 提交。
- **状态/API 兼容性：** Storage 公共读取/写入接口保持；数据文件仍为 JSON；新增内部 journal 文件仅在未完成事务时存在；明确只支持一个进程/worker。
- **新增测试：** 多线程 task/log 写、写中途失败保留旧有效文件、journal 恢复、重启读取、无 invalid JSON、跨记录 bundle 一致。
- **验收标准：** 单进程并发不丢记录；任一单文件写失败不会损坏旧 JSON；崩溃后重启要么完成 journal，要么明确失败，不出现静默半状态。

### PA-01 / PA-02 / TEST-01 — Patch 部分失败与发布门禁测试

- **涉及文件：** `patching.py`、`editing_service.py`、全部相关测试。
- **根因：** 多文件 replace 逐项完成但异常不携带 ledger；parser 未完整校验 new coordinate/no-op/Windows 等价目标；现有测试偏 happy path。
- **最小修复：** `PatchApplyError` 携带 attempted/replaced files；失败时在 reset 前采集实际 diff/manifest；严格校验 hunk 双侧位置、语义变化、控制字符和 Windows canonical duplicate；将所有 parser/path 异常统一为结构化 422。
- **状态/API 兼容性：** 正常 Patch subset 不变；以前被宽松接受的 malformed/no-op Patch 改为 422；报告新增部分 apply 证据字段时保持旧字段。
- **新增测试：** 多文件第 N 次 replace 失败、rollback 成功/失败、case-fold duplicate、no-op、错误 new coordinate、控制字符、解析边界。
- **验收标准：** 部分写永远有准确 ledger/report；rollback 后无残留；所有 malformed 输入稳定返回 422，不留下 PATCH_PROPOSED/PENDING 半状态。

## 状态与文档决定

- `SUCCESS` 继续表示分析阶段成功，`SUCCEEDED` 表示批准 Patch 已应用、测试通过且最终 manifest 验证通过。
- `CANCELLED` 在单次 editing attempt 内是终态；为保持现有兼容，task 可以从 CANCELLED 启动新的 analysis 或新 Patch attempt，但旧 attempt 不可恢复 execute。
- rollback 无论成功与否，执行 attempt 的最终 task 状态均为 `FAILED`；通过 `rollback_succeeded`、`rollback_error`、manifest hashes 和 source integrity 字段区分恢复结果。
- README 明确：只运行可信仓库和用户显式授权命令；不是 OS sandbox；单进程/单 worker；不写回 source；不支持多租户或公网无认证部署。
